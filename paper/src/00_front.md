# Who Read the Edit? Repairing Cached Attention State after Mid-Context Changes

**Ashraf Taha**  
Independent researcher, Cairo, Egypt  
ashraf.taha.career@gmail.com

### Abstract

LLM agents edit the middle of their context: they clear old tool results, replace stale documents and receive results out of order. A prefix cache then discards everything after the edit. Recent work asks how little of that suffix must be recomputed; we ask which cached tokens carry the error, and what that means for engine design. When a supporting document is deleted, reusing the stale suffix is {{e1p.ratio_min}} to {{e1p.ratio_max}} times further from a full re-prefill if the question was cached before the edit than if it arrives after it: the error travels through cached tokens that read the changed content and are then read by the output. How much each cached token attended to the edited span is computed at prefill anyway, and how much the next input attends to each cached token takes one extra pass. Fusing the two rankings and recomputing 10% of the suffix removes {{robust_exp.rrf.range_qa}} of the error in {{robust_exp.rrf.count_qa}} experiments on {{scope.models}}, and {{robust_exp.rrf.not_behind_phrase}}, agent transcripts included, no policy that ignores prompt roles does significantly better. Either signal alone, or a fixed window, falls behind. Three findings bear on designs now being proposed. Leaving a gap where content was deleted, instead of renumbering, changes up to {{e15.max_changed}} of answers at 1,024 positions. Rewriting 16-bit keys in place drifts with the square root of the number of edits, while rotating the query gives the same logits with no writes. And a partial repair does not erase: the stale cache keeps answering from a deleted document, and a 10% repair reduces that without removing it. All experiments ran on one laptop GPU; a roofline estimate for a fused engine puts a 1% repair of a 16k-token suffix at {{e24.16384.cost.0.01}} of the cost of a re-prefill.
