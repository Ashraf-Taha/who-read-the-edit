## 5. Repairing what the reader needs

### 5.1 Policies

A repair recomputes a chosen set of suffix tokens through all layers while every other cell is read from the cache, and the chosen tokens see each other's new cells. A contiguous block that starts at the edit comes out exact, because every cell it reads is exact. Any other choice is an approximation, because a recomputed token still reads the stale cells around it. The question is which approximation removes the most error for a given budget.

**A first-order account.** Take one head of one layer and a token $r$ whose output matters, a token of the new input or the next generated token. Its attention output is $o_r = \sum_j \alpha_{rj} v_j$, so errors $\Delta v_j$ in cached values reach it as $\Delta o_r \approx \sum_j \alpha_{rj}\, \Delta v_j$. After a deletion, cached token $j$ had put mass $m_j$ on the deleted span. Its stale read of that layer therefore differs from the correct one by exactly $m_j(\bar v_{\text{removed}} - \bar v_{\text{rest}})$, where the bars are attention-weighted means over the removed and the remaining keys. The difference enters $j$'s residual stream and its keys and values at later layers, so to first order the error that reaches $r$ through $j$ scales with $\alpha_{rj} m_j$, the weight of a two-step path from the edit through $j$ to $r$. This is a heuristic, not a bound. It ignores how errors in cached keys shift attention, longer paths through other stale tokens, and the new distance between every query in $S$ and the prefix. What it does is tell a policy which two quantities to measure.

**Our policies.** The **bridge score** is the product $m_j \rho_j$, with both factors averaged over layers and heads. ProphetKV defines its ideal score as attention times true deviation, which needs the re-prefill, and falls back to attention alone [@wang2026prophetkv]. For documents cached separately there is no cheap stand-in for the deviation; in a live edit there is one, exposure, and the bridge score makes that substitution. **Rank fusion** (reciprocal rank fusion with $k = 60$) adds the reciprocal ranks of the two signals instead of multiplying their values, which gives both signals the same say whatever their scales. **Reader-first repair** recomputes one stale segment whole and then spends the rest of the budget by exposure. The segment is either the cached question, when the engine knows the prompt's roles, which we write as reader-first (given), or else the stale segment the new input attends to most per token, reader-first (found). Apart from reader-first (given), no policy here needs to know which segment plays which role, and we call these policies role-free.

**Baselines.** Each existing selector bets on one kind of evidence. A **boundary window** recomputes the tokens right after the edit; it is the edit-local window of Mao et al. [@mao2026contiguity] and one of KVEraser's baselines [@li2026kveraser]. A **tail window** recomputes the tokens just before the new input. **EPIC's selection** takes the first tokens of each document [@hu2025epic]. **CacheBlend's criterion** takes the tokens whose cells moved most at the first layer that depends on context [@yao2025cacheblend], following the rule LMCache's open-source implementation uses by default [@lmcache_inprocess] (Appendix C checks that our variant picks almost the same tokens). **Reader attention** alone is ProphetKV's practical score [@wang2026prophetkv] and the stale-query attention baseline of Mao et al. **Recorded exposure** alone follows Cache-Craft's recorded inter-chunk attention [@agarwal2025cachecraft]; Yu et al. run the same quantity, computed by replaying the suffix, as a baseline [@yu2026budgeted]. These are the selection rules of the cited systems as we implemented them, not the systems themselves. As a reference that needs the re-prefill we also run the **oracle score**, true cell deviation times reader attention, which is ProphetKV's ideal. It is not an upper bound: a recomputed token still reads its stale neighbours, so a token's own deviation is not what recomputing it buys.

### 5.2 The main experiment

We delete one supporting document and reorder the prompt so that the edited document is the 2nd, 5th or 8th of ten. The question is cached and sits in one of three places: right after the edited document, in the middle of the remaining documents, or after all of them. Only the tokens that open the assistant's reply are new input. Each model sees {{e2c.qwen1.5b.questions}} questions, 12 per position of the edited document, each in all three placements, so {{e2c.qwen1.5b.n}} cases per model. The position of the edited document sets the suffix length, about {{e2c.qwen1.5b.lead1.suffix}}, {{e2c.qwen1.5b.lead4.suffix}} and {{e2c.qwen1.5b.lead7.suffix}} tokens on Qwen2.5-1.5B. We call the first two **long suffixes** and the third a **short suffix**, where 10% of the suffix is about {{e2c.qwen1.5b.short.budget}} tokens, close to the length of the question. Each policy ranks the suffix tokens, and the top 5%, 10% or 20% are recomputed in one pass. Table {{#main_strata}} gives the main policies at 10%; Appendix C gives every policy we ran, with intervals, medians, other budgets and per-case distributions.

Windows work only when the reader falls inside them. The boundary window removes {{e2c.place.adjacent.boundary.removed.range}} of the no-repair KL when the question sits right after the edited document, and nothing measurable when it sits further on ({{e2c.place.middle.boundary.removed.range}} and {{e2c.place.end.boundary.removed.range}}). The tail window is its mirror image: it removes {{e2c.place.end.tail.removed.range}} with the question at the end and nothing measurable elsewhere ({{e2c.place.adjacent.tail.removed.range}} and {{e2c.place.middle.tail.removed.range}}). This is the adjacency effect Mao et al. report for the edit-local window [@mao2026contiguity]. Rank fusion, which is not told where the question is, removes {{e2c.place.adjacent.rrf.removed.range}}, {{e2c.place.middle.rrf.removed.range}} and {{e2c.place.end.rrf.removed.range}} in the three placements. EPIC's selection and CacheBlend's criterion do no better than the windows; together, these four leave {{e2c.windows_left_min}} to {{e2c.windows_left_max}} of the no-repair KL.

Each signal alone falls short in a predictable way. Reader attention alone leaves {{range:e2c.*.left.reader}} of the no-repair KL, depending on the model: after one interior edit most of what the reader attends to is clean, so the budget goes to tokens that never read the edit. Recorded exposure alone spends the budget on tokens that read the edit but are not read, and does well only when the question sits right after the edited document. On Qwen2.5-1.5B it leaves {{e2c.qwen1.5b.place.adjacent.exposure}} nats there, against {{e2c.qwen1.5b.place.end.exposure}} with the question at the end.

Combined, the two signals leave {{e2c.left_combined_min}} to {{e2c.left_combined_max}} of the no-repair KL, pooled over layouts. The main run tested the bridge score against every other policy, so the paired results are for it. It has lower KL than reader attention alone in {{range:e2c.*.vs.reader.win}} of cases (Holm-adjusted $p \le$ {{e2c.qwen0.5b.vs.reader.holm}}), and significantly lower KL than exposure alone on {{e2c.bridge_vs_exposure.significant}} (Table {{#C:ablation_paired}}). The bridge score's mean KL is {{e2c.qwen0.5b.ratio.bridge_rrf}}, {{e2c.qwen1.5b.ratio.bridge_rrf}} and {{e2c.smol1.7b.ratio.bridge_rrf}} times rank fusion's on the three models, an interval above 1 on {{e2c.bridge_rrf.rrf_better}} of them and below 1 on {{e2c.bridge_rrf.bridge_better}}.

Suffix length decides between token scores and reader-first repair. With a long suffix, rank fusion has the lowest KL of the practical policies on all three models, and reader-first (found) is significantly worse than rank fusion on each ($p \le$ {{e2c.long.segment_vs_rrf.p_max}}; Table {{#C:strata_tests}}). With a short suffix the order reverses. The question then fills most of a budget of about {{e2c.qwen1.5b.short.budget}} tokens (it is longer than the whole budget in {{range:e2d.*.lead7.question_over_budget}} short-suffix cases), and token-level scores spread that budget over the two documents in the suffix instead. Reader-first (found) beats rank fusion on all three models, significantly on {{e2c.short.segment_vs_rrf.significant}} (Section 5.4).

Better selections exist. On {{e7.qwen1.5b.n}} further cases, the practical policies leave at least {{e7.qwen1.5b.over_greedy_practical_min}} times the KL of a greedy search over {{e7.qwen1.5b.block}}-token blocks that measures each block's effect on the KL. That search is scored on the cases it was chosen on, so it overstates what is reachable, and rank fusion was not run there (Appendix E). Whether a practical rule can close the gap is open. The oracle score is no bound either, for the reason given in Section 5.1: the bridge score has lower KL than it in {{range:e2c.*.vs.oracle_reader.win}} of cases. For the same reason a repair can be worse than none, which happens in {{e2c.harm.bridge.min}} to {{e2c.harm.bridge.max}} of the {{e2c.qwen1.5b.n}} cases per model for the bridge score, {{e2c.harm.rrf.min}} to {{e2c.harm.rrf.max}} for rank fusion and {{e2c.harm.reader.min}} to {{e2c.harm.reader.max}} for reader attention alone.

The first reply token does not drive these results. Leaving it out, the bridge score still has lower KL than reader attention alone in {{e2c.qwen1.5b.later.bridge_vs.reader.win}} of the {{e2c.qwen1.5b.later.n}} cases with longer replies on Qwen2.5-1.5B ($p$ = {{e2c.qwen1.5b.later.bridge_vs.reader.p}}; Table {{#C:later}}). After a 10% repair by the bridge score the KL is below that of the harmless document swap of Section 2.3 in {{range:e2c.*.noise.kl_tf.below.bridge}} of cases, against {{range:e2c.*.noise.kl_tf.below.stale}} without repair.

### 5.4 Recomputing a reader whole

Recomputing a whole segment is a form of the contiguity that Mao et al. and Yu et al. argue for: a recomputed token reads recomputed neighbours instead of stale ones [@mao2026contiguity; @yu2026budgeted]. In our data it pays off when the suffix is short, so that the cached question takes most of the budget and few other stale tokens compete for it. In the main experiment's short-suffix stratum, reader-first (found) has the lowest mean KL of the practical policies {{e2c.short.first_lowest}}. In the replication's short-suffix stratum its mean KL is lower than rank fusion's {{e16.short.below_rrf}} and the lowest of the practical policies {{e16.short.lowest}}{{e16.short.exceptions}}. With long suffixes, long contexts and the needle task, rank fusion or the bridge score does better (Tables {{#main_strata}} and {{#robust_experiments}}). Reader-first (found) still has the best pooled score in the main experiment's row of Table {{#robust_experiments}}: the short-suffix cases have the larger KLs, so its gains there outweigh its losses on long suffixes in the pooled mean. Yu et al. find a much stronger effect of grouping: with the same token scores, refreshing whole text regions recovers far more exact-match answers than refreshing the top tokens one by one [@yu2026budgeted]. Their metric is exact match on list-valued answers and ours is KL over the reply, and we did not run their region allocation, so whether grouping our scores into regions would help is open.

Two things limit reader-first repair. The first is that the engine has to find the segment. An engine that tracks segments but not their roles can take the stale segment the new input attends to most per token. In the main experiment that segment is the question in {{e2d.found_all}} of cases, but only because the question was also the shortest stale segment: in the replication on Qwen2.5-1.5B, a rule that ignores attention and picks the shortest segment finds it just as often ({{e16.qwen1.5b.plain.shortest_finds}} cases, and {{e16.qwen1.5b.plain.density_finds}} for the attention rule). When two notes of about eight tokens are added to the suffix, one right after the edited document and one at its end, the attention rule picks the note next to the new input and no longer finds the question on any model ({{range:e16.*.decoy.density_finds}} cases on each). Reader-first repair then leaves {{e16.qwen1.5b.decoy.density_exposure}} nats on Qwen2.5-1.5B, against {{e16.qwen1.5b.decoy.question_exposure}} when the question is given, while the bridge score and rank fusion, which do not use segments, leave {{e16.qwen1.5b.decoy.bridge}} and {{e16.qwen1.5b.decoy.rrf}}, about what they leave without the notes (Table {{#D:decoy}}). A long new input dilutes the rule as well (Table {{#E:longq}}). Reader-first repair is safe only when the engine knows which segment is the reader, as agent frameworks usually do for the latest user turn.

The second is that the segment has to be where the damage runs. On the needle task the attention rule finds the question every time, and recomputing it first is still much worse than the bridge score: at 1,000 tokens and 2% of the suffix it makes {{e3r.qwen1.5b.1000.segment_exposure@0.02.k}} replies exact, against {{e3.qwen1.5b.1000.bridge@0.02.k}} (McNemar $p$ = {{e3r.qwen1.5b.1000.segment_vs_bridge.0.02.p}}). Here the damage runs through the retained needle, which read the erased one and is read by the question, and the bridge score spends its budget on both ends of that path. On the real transcripts the most-read stale segment is usually the agent's latest turn ({{e21.picked_last.range}} transcripts). When the first tool result is cleared, recomputing that turn first is {{e21.clear1.first_vs_rrf}}; when the second is cleared, it is {{e21.clear2.first_verdict}}. Recomputing a reader helps only when its own stale reads are the problem.

Inserts favour reader-first repair. When a document arrives late, nothing was recorded about it, because the cached suffix never saw it, so exposure has to be estimated while reader-first needs only the reader pass. On the main experiment's cases read as inserts, recomputing the most-read segment first and then the tokens with the most reader attention has lower mean KL than the product of reader attention and an exposure estimate from kept queries on {{e2e.first_lower}} models tested, significantly on {{e2e.first_significant}} (Table {{#E:insert_reader}}; the estimate is described in Appendix E).

### 5.5 Does repair erase what was deleted?

Content is often removed because it is outdated, retracted or private, and then it matters whether the deleted content can still be read, not only how close the answer is to a re-prefill. Three measurements bear on this. First, in the main experiment on Qwen2.5-1.5B the stale cache still answers from a deleted supporting document: its replies have a higher token F1 against the dataset's answers than the re-prefill's ({{acc.qwen1.5b.f1_minus_truth.stale}}, interval over questions), and after a 10% repair by the bridge score the excess is {{acc.qwen1.5b.f1_minus_truth.bridge}}. Second, a fresh request to quote the deleted document's first sentence finds no excess for it in the stale suffix, against our hypothesis H4. Relative to the re-prefill, the stale state changes that sentence's log-probability by {{e16.qwen1.5b.leak.stale}} nats per token on Qwen2.5-1.5B, while the state that still holds the document raises it by {{e16.qwen1.5b.leak.present_gap}} (Table {{#D:leak}}). Third, on the needle task the erased value never reappears, with or without repair. These fit Section 4: what leaks is what the cached readers took from the deleted document, and a new reader of the stale documents recovers almost nothing. A targeted repair serves the next answer and removes most of the readers' share for it, but it guarantees nothing about other readers, and where removal is required only the exact state counts. Yao et al. prove that exact unlearning in a stateful agent needs the suffix after the forgotten content replayed [@yao2026forgetting]; the sweep of Section 6 is that replay.

### 5.6 Cost

In our reference engine on Qwen2.5-1.5B, re-prefilling a {{e6.qwen1.5b.suffix}}-token suffix took {{e6.qwen1.5b.reprefill}} s, the reader pass {{e6.qwen1.5b.reader}} s and recomputing 10% of the suffix {{e6.qwen1.5b.repair.0.1}} s (medians over {{e6.qwen1.5b.n}} cases, best of three runs each). A 10% repair, reader pass included, therefore costs {{e6.qwen1.5b.ratio.0.1}} times as much as re-prefilling the suffix, measured at this length only. Recomputing a share of the tokens costs more than that share of a re-prefill, because every recomputed token attends over the whole context and each pass has fixed costs per layer. Spreading the tokens does not add to this in our engine: recomputing 10% of the suffix as {{e23.qwen1.5b.runs.0.1}} separate runs costs the same as recomputing one block of the same size (a time ratio of {{e23.qwen1.5b.ratio.range}} at budgets from 1% to 20%). With a long new input the reader pass need not cover all of it: with reader attention from its last 16 tokens only, the bridge score reaches {{e11.qwen1.5b.512.last16.bridge.ratio}} and {{e11.qwen1.5b.2048.last16.bridge.ratio}} times the mean KL it reaches with the whole input (512 and 2,048 tokens). We see no sign of harm, but the intervals are too wide to show it is as good.

We have not built a fused engine, so Appendix A estimates one with a roofline model: each pass costs the larger of its FLOPs at peak compute and its memory traffic at peak bandwidth. Two things follow. First, a repair pass and a reader pass each read all the weights once, so a repair with its reader pass costs at least two reads of the weights, however few tokens it recomputes. For a 1,024-token suffix, a 10% repair with its reader pass costs {{e24.1024.cost.0.1}} of a re-prefill; for 16,384 tokens, a 1% repair costs {{e24.16384.cost.0.01}} and a 10% repair {{e24.16384.cost.0.1}} (Table {{#A:costmodel}}). Repair pays off most for long suffixes. Second, spreading the repaired tokens over the suffix costs up to {{e24.spread.max_extra}} more than a block right after the edit, because later tokens attend over more keys. The model has no term for gathering scattered rows, which a fused kernel may pay, and the reader pass needs a kernel that returns per-key attention sums, which standard fused attention does not.

Exposure is one number per token and earlier segment, about {{mem.qwen1.5b.exposure}} MiB for {{mem.tokens}} tokens in {{mem.segments}} segments, which is {{mem.qwen1.5b.exposure_share}} of a 16-bit KV cache on Qwen2.5-1.5B and {{mem.qwen7b.exposure_share}} on Qwen2.5-7B (Table {{#E:memory}}). Our engine materialises attention weights, and recording exposure there added {{e6b.qwen1.5b.exposure_overhead}} to prefill. A fused kernel does not materialise them; it would keep one running sum per earlier segment beside the running softmax normaliser, rescaled with it. In a tiled emulation of such a kernel the per-segment sums match the materialised mass to within {{e14.exposure.error}}. When a tile of keys lies within one segment, its contribution is the tile's row sum, which the online softmax computes anyway, so we expect the extra cost to be small, though we have not measured it.
