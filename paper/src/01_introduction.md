## 1. Introduction

Picture an agent twenty turns into a task. Its context holds a system prompt, the user's request and a long run of tool calls and their results. To save room, it replaces an old search result with a one-line note. Anthropic's context editing does exactly this once a conversation passes a threshold, and its documentation warns that clearing invalidates the cached prompt prefix [@anthropic2025contextediting]. Every token after the cleared result is still in the KV cache, but a prefix cache cannot use it, because the shared prefix now ends at the edit. The engine recomputes the whole suffix, often thousands of tokens, before it can answer. The same happens when a retrieved document turns out to be stale, when a user corrects a fact, when a parallel tool call returns after a later one was appended, and when sub-agents' findings are merged. Models that manage their own context make such edits routine [@shao2026clm], and Stream2LLM, which starts prefill while retrieved content is still arriving, reports that more than 10% of requests invalidate over 10,000 tokens at every load it tested [@bachkaniwala2026stream2llm].

Reusing the suffix after an edit raises two problems. Its tokens now sit at new positions, and their keys and values were computed while attending to a context that no longer exists. The first problem is solved: under rotary position embeddings a cached key can be moved exactly [@yao2025cacheblend; @llamacpp3228; @he2025pie]. The second is not. Several designs correct the positions and accept the rest of the error. PIE does so after code edits [@he2025pie], Leyline calls its splice "positional, not informational" [@ma2026leyline], a vLLM proposal calls suffix reuse "explicitly approximate" [@vllm58537], and the Suffix Cache Reuse of context language models moves the surviving keys without repairing them [@shao2026clm].

A short line of recent work repairs the suffix instead, by recomputing a small share of it. Mao et al. treat this as budgeted recomputation after a document edit and find that a contiguous window right after the edit works well when the text that depends on the edit sits next to it, and much less well when it does not [@mao2026contiguity]. Yu et al. study deletions in agent contexts and refresh whole text regions chosen by their relevance to the next query [@yu2026budgeted]. Li shows that after a field changes, the model's conclusion about it already lives in downstream tokens written at prefill, which the decision then reads [@li2026notes]. These papers, and the earlier selectors for composing documents that were cached separately [@yao2025cacheblend; @hu2025epic; @agarwal2025cachecraft; @wang2026prophetkv], each choose what to recompute from one kind of evidence, such as where the edit is, how much the next query attends to a token, how far a token's cells moved at an early layer, or how much a token attended to the deleted span. Most of these selectors were built for documents that never saw each other and for a query that is always new input. A live edit is different. The cached suffix did see the content that changed, so how much each token read of it is already known, and the token that reads the damage next is often itself cached.

We start from where the error goes. After an edit it reaches the output along two-step paths: from the changed span to a cached token that read it, and from that token to the input that reads it next. We call the cached tokens on strong paths the **readers of the edit** and find them with one signal per step (Figure {{#fig_paths}}). A token's **exposure** is how much it attended to the edited span. The suffix was encoded with the span present, so prefill has already computed it, and an engine only has to keep it. A token's **reader attention** is how much the next input attends to it, which costs one pass of that input over the stale cache. Either signal alone sees half of the path. A first-order argument suggests multiplying them, which we call the **bridge score**; fusing their two rankings instead, which we call **rank fusion**, gives both signals the same weight whatever their scales.

We make four contributions.

1. **Where the damage sits** (Section 4). After the same deletions, reusing the stale suffix is {{e1p.ratio_min}} to {{e1p.ratio_max}} times further from the re-prefill when the question was cached before the edit than when it arrives after it, and the fresh reading is the closer one in {{e1p.fresh_lower_min}} to {{e1p.fresh_lower_max}} of cases ($p \le$ {{e1p.p_max}}). This agrees with Li's causal finding [@li2026notes] and turns it into something a cache can measure.
2. **A combined selector** (Section 5). Recomputing 10% of the suffix (5% on a needle task), chosen by rank fusion of exposure and reader attention, removes {{robust_exp.rrf.range_qa}} of the no-repair error in {{robust_exp.rrf.count_qa}} experiments outside the agent transcripts, on {{scope.models}}. Counting the transcripts, {{robust_exp.rrf.not_behind_phrase}}, no policy that ignores prompt roles is significantly better. Reader attention alone, which is ProphetKV's practical score [@wang2026prophetkv], is significantly behind the best in {{robust_exp.reader.behind}} experiments, and exposure alone in {{robust_exp.exposure.behind}}. A window right after the edit removes {{e2c.place.adjacent.boundary.removed.range}} of the error when the cached question is next to the edit and almost none ({{e2c.place.middle.boundary.removed.range}}) when it sits further on; rank fusion removes {{e2c.place.adjacent.rrf.removed.range}} and {{e2c.place.middle.rrf.removed.range}} in the same two layouts.
3. **When to recompute a reader whole** (Section 5.4). Recomputing the cached question first and then filling the budget by exposure is best when the suffix is short and the question takes most of the budget. It needs the engine to know which segment is the question. Picking that segment from attention fails when a shorter segment sits closer to the new input, and recomputing the question first does not help when the damage runs through another segment, as on a needle task.
4. **A runtime and a cost estimate** (Sections 5.6 and 6). A small runtime tracks which cells are still exact after any sequence of edits, repairs for the next reader and sweeps back to the exact state. For a fused engine, a roofline estimate puts a 1% repair of a 16k-token suffix, reader pass included, at {{e24.16384.cost.0.01}} of the cost of a re-prefill, but a repair of a 1k-token suffix still at {{e24.1024.cost.0.1}}, because every pass reads all the weights once.

Several results apply directly to engine designs under discussion. A vLLM proposal for context editing masks deleted spans without renumbering the positions after them [@vllm58537]. Without any staleness, a gap of 1,024 positions changes up to {{e15.max_changed}} of greedy answers, and with a fresh reader, a gap the size of one deleted document moves the output more than reusing the stale cells does in {{e1.hole.worse}} of {{e1.hole.groups}} test groups (Section 4.3). Many systems relocate cached state by rewriting its keys [@yao2025cacheblend; @ma2026leyline; @liu2026redknot]; in 16-bit storage the error of the rewritten keys grows with the square root of the number of rewrites, while rotating the query once per offset gives the same logits and writes nothing (Section 3). And content is often deleted because it is wrong or private. The stale cache keeps answering from a deleted document, a 10% repair reduces this without removing it, and only a sweep back to the exact state removes it (Section 5.5).

All experiments use models of 0.5B to {{scope.max_params}} parameters on one laptop GPU and measure how close the repaired state stays to a full re-prefill, not serving latency; Section 8 lists what this setup cannot show.
